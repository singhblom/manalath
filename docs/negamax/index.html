Summary

The search tiers of the AI are a standard game-tree search: negamax with alpha-beta pruning, iterative deepening, and a hand-written evaluation at the leaves. Three things make it Manalath-specific. Every node checks for wins and suicides one move ahead before it does anything else. Suicidal moves are never searched at all. And the evaluation counts safe moves and small groups rather than material, because in Manalath a stone is as likely to be a liability as an asset.

The problem

A quick recap of the rules as packages/shared/src/game.js implements them. The board has 61 hexagonal cells. On your turn you place one stone of either colour. No group may ever grow beyond five stones. At the end of your turn, if a group of your own colour has exactly four stones (a quart), you lose. If it has exactly five (a quint), you win. A quart beats a quint, so you can't escape a quart by making a quint somewhere else.

A move is a cell and a colour, so the opening position has 122 of them. Games between the bots average about 20 moves. Looking even three moves ahead naively means a million positions, and each one needs its groups checked. The job of the search is to look as far ahead as it can afford and to spend that budget on the lines that matter.

Negamax

The classic formulation is minimax. Build a tree of positions, score the leaves from one player's point of view, then work upwards. At a node where that player moves, take the highest child score. Where the opponent moves, take the lowest. The value at the root is what the player can guarantee against best play, as far as the tree reaches.

Negamax is the same algorithm with one trick. Score every position from the point of view of the player to move there. Then a node's value is the best child value negated, because a position worth +5 to my opponent is worth −5 to me:

value(node) = max over moves m of  −value(child after m)

This works because min(a, b) = −max(−a, −b). There's no separate min branch, and one function handles both players. The only requirement is that the leaf evaluation is from the side to move, which is how evaluate() is written.

Alpha-beta pruning

Most of the tree in Figure 1 doesn't need to be looked at. Suppose White has already found a move worth +3. While exploring a second move, White sees that Black has a reply leaving White only −4. There's no need to look at Black's other replies. They could only make this move worse for White, and it is already worse than +3.

Alpha-beta makes that bookkeeping systematic by passing a window (α, β) down the tree, from the point of view of the player to move:

  • α is the score the player to move is already guaranteed elsewhere. Anything below it is not interesting.
  • β is the most the opponent will allow. If this node reaches β, the opponent will steer away from it one level up.

A child is searched with the window (−β, −α), the same window seen from the other side. As soon as α ≥ β, the remaining moves at the node are skipped: a cut-off. The value at the root doesn't change. Only the amount of work does.

Here is the whole search function from ai.js. Apart from the Manalath checks at the top, it is the textbook version:

function negamax(board, p, depth, alpha, beta, ctx) {
  if (++ctx.nodes > ctx.maxNodes || ((ctx.nodes & 255) === 0 && performance.now() > ctx.deadline)) throw new Timeout();
  const a = analyse(board);
  const moves = legalMoves(a);
  if (!moves.length) {
    // forced pass: end conditions for p still apply
    return a.quarts[p] ? -(WIN + depth) : a.quints[p] ? WIN + depth : 0;
  }
  const mine = classify(a, p, moves);
  if (mine.wins.length) return WIN + depth;
  if (!mine.safe.length) return -(WIN + depth);
  if (depth === 0) return evaluate(a, p, moves, mine);
  let best = -Infinity;
  for (const [i, c] of ordered(a, p, mine.safe)) {
    board[i] = c;
    const v = -negamax(board, 3 - p, depth - 1, -beta, -alpha, ctx);
    board[i] = 0;
    if (v > best) best = v;
    if (v > alpha) alpha = v;
    if (alpha >= beta) break;
  }
  return best;
}

It is fail-soft: when it cuts off it returns the best score it found, which may lie outside the window, rather than clamping it to α or β. The board is mutated in place and restored after each move, so no positions are copied.

What Manalath adds

A free extra ply of tactics

Before recursing, every node sorts its legal moves into three piles with classify(). For each move it works out what the end-of-turn check would say for the player who placed it:

  • Wins make a quint (and no quart). If there is one, the node is decided and the search stops here.
  • Losing moves leave a quart of your own colour. They are dropped, never searched.
  • Safe moves are everything else. Only these are searched.

If there are no safe moves, the node is lost. This is Manalath's zugzwang: the player who runs out of safe moves loses, even with plenty of empty cells left.

So every node, leaves included, sees one move further ahead than its depth says, for the cost of a few lookups per move (see §10). It also shrinks the tree. Late in the game many placements are suicidal, and discarding them before recursion is pruning that costs nothing.

One consequence is worth spelling out. classify checks all of the mover's groups, not just the one touched. If your opponent leaves you a quart, every move that doesn't deal with it loses. A move that grows it to five is a win, since a quint without a quart wins. That's why handing someone a quart only works if it is sealed, so that every extension would make an illegal group of six (see Figure 3 of the handicap study).

Scoring wins by distance

A decided node returns WIN + depth or −(WIN + depth), with WIN = 10000 and depth the plies remaining. A win found higher in the tree has more depth remaining, so it scores higher. The search prefers the fastest win and, when losing, the slowest loss, which gives a human opponent the most chances to go wrong. Evaluation scores stay far below 10,000, so any score above WIN − 100 means "forced".

Passes

When no cell accepts either colour the player must pass, and the end-of-turn check still applies to them. This is rare enough that the search just scores it and stops.

The evaluation

When the depth runs out, evaluate() scores the position for the player to move. It adds up five hand-tuned terms:

TermWeightReasoning
Opponent's immediate wins−40 eachPlacements that would give the opponent a quint if it were their move. These are threats you have to answer.
Safe moves, yours minus theirs+0.5 eachMobility. The endgame is decided by who runs out of safe moves first.
Groups of 3 / 2 / 1+6 / +2 / +1Your colour counts for you, theirs against. A three can't be grown by its owner (that makes a quart) and won't be grown by the opponent (that offers a quint), so it is a lasting threat.
Groups of 4 or 50Already decided by the one-move-ahead check.
Centrality+0.3 × (4 − d)For each of your stones, d steps from the centre. Central stones have more room around them.

The evaluation is not symmetric. The centrality term only counts the mover's stones, and the threat term only counts the opponent's wins, since the mover's own wins were already caught above. Negamax doesn't need symmetry. It only needs every leaf scored from the side to move, and it negates on the way up.

Move ordering

Alpha-beta only cuts off when a good move comes early. ordered() gives each safe move a quick score and sorts them best first:

  • −distance from the centre, so central moves go first.
  • +30 if the opponent could win by placing the same colour on the same cell. Taking it first removes that option.
  • −1 for placing the opponent's colour, as a tie-breaker. Your own colour is usually the more constructive choice.

This is cheap and crude. It doesn't reuse anything from earlier iterations, such as the best move found at the previous depth. Even so, it pays for itself. On a sample of 25 early-game positions, finishing depth 2 took these median node counts:

Deepening on a budget

The search doesn't pick a depth up front. playTier() uses iterative deepening: it searches to depth 1, then 2, then 3, keeping the result of the last depth that finished.

  • Depth 1 always runs to completion, with no node limit, so there is always a move to play.
  • Deeper iterations share one node budget: 3,000, 12,000, 50,000 or 150,000 nodes for difficulty tiers 4 to 7. When the budget is spent, negamax throws Timeout. The unfinished iteration is thrown away and the previous depth's move is played.
  • A 4-second wall-clock cap is a backstop for slow devices. Budgeting in nodes means a given difficulty plays at the same strength on a phone and a desktop.
  • If an iteration finds a forced win or loss, deepening stops. Looking further can't change the result.

At the root, rootSearch() does what negamax does, but keeps every move that ties for the best score and picks one at random, so the bot doesn't play the same game twice.

A tie-breaking bug

Writing this doc turned up a bug in how the root collected ties. It is fixed as of engine version 2 (ENGINE in ai.js), but it is a good lesson in what alpha-beta bounds do and don't tell you. After the first root move sets α, each later move is searched with the window (α, ∞) from the root's side. That search only answers "is this move better than α?". When the answer is no, fail-soft returns an upper bound, and nothing stops that bound from being exactly α. The root then compares with v === best, sees a tie, and adds the move to the list for the random pick, even if its true score is much lower.

This happens most with forced wins, because those scores are whole numbers. Say the first root move wins by force at depth 2, so α = 10,000. For any later move, if the opponent's first reply the search tries leaves you an immediate win, that reply scores exactly −10,000 for the opponent. That reaches the child's β = −α, so the child cuts off and the root sees exactly 10,000: a "tie". It doesn't matter that another reply would have defended.

The fix is a one-line change in rootSearch: search later moves against a window just below α, so that a move which really ties has to prove it:

const v = -negamax(board, 3 - p, depth - 1, -Infinity, -alpha + TIE_EPS, ctx);

A move whose true score is α now returns α exactly. A worse one fails low, strictly below α, and drops out of ties. A cheaper alternative is to drop the random tie-break once the score is a forced win, and play the first winning move found. We went with the exact window, since it also keeps the variety of the random pick.

The strength study was measured with the bug in place, so we re-rated the ladder afterwards with another 920 games. (These are engine 2 figures; §10 has the current ones.) The tiers without search came out the same within noise, as they should. The search tiers gained a lot:

Where the time goes

Engine 2 spent most of its time checking group sizes. Every classify placed each of up to 122 moves and flood-filled the whole board to judge it, and at depth 0 evaluate classified the mover's moves a second time. In midgame positions it managed about 6 nodes per millisecond. The 50,000-node tier needed six seconds per move and hit the 4-second safety cap on 22 of 27 moves we timed, so its rating was really a rating for four seconds on one Mac.

Engine 3 makes two changes:

  • One group labelling per node. analyse() flood-fills the board once, recording each group's size and how many quarts and quints each colour has. A move's effect then follows from its neighbours: the group it makes is one stone plus the distinct neighbouring groups of that colour, and the mover's quart and quint counts change by what it absorbs and creates. Legality, classification and move ordering become a few lookups per move.
  • No second classification at the leaves. evaluate now receives the analysis, move list and classification that negamax has already computed.

The search makes exactly the same decisions as before. 1,476 root searches at depths 1 to 3 returned identical scores, moves and node counts. It now runs at about 220 nodes per millisecond, 35 times faster, so the 50,000-node tier thinks for about a quarter of a second and never meets the time cap.

Because the top tier now gets its full budget, we re-rated the ladder, and with games now cheap we added a tier above it: 150,000 nodes, about 0.85 seconds per move at the median. The ratings below pool 10,000 engine-3 games, with 200 to 400 per pairing.

Two things came out of the re-rating besides the numbers. First, the first-move advantage is not one number. Up to difficulty 5 it is small, around 0 to 50 Elo. Once both bots reliably search three plies it jumps to about 200, so between two difficulty-7 bots the first player wins roughly three games in four. The rating fit now gives each difficulty its own first-move term. It is also a result about the game: strong Manalath may be strongly biased towards the first player, and a swap rule or other balancing may be worth a look.

Second, the absolute scale is only as good as its lowest links. Every rating is chained up from random play, so noise in the easiest pairings shifts every rating above them. Two independent runs of about 5,000 games disagreed by up to 160 at the top, mostly because random play against difficulty 0.5 came out differently. Pooling both runs, which rate-ai.js now does whenever a game's two bots still play the same tiers, halves that risk. Gaps between neighbouring difficulties are much better determined than the absolute values.

What could make it stronger still, roughly in order of effort:

  • Bigger budgets. The 150,000-node tier finishes depth 4 in 10 of the 12 positions we sampled. Much beyond that, slow phones start hitting the 4-second cap again, so further gains have to come from searching smarter.
  • Keep the partial iteration. When the budget runs out mid-iteration, the root moves already searched at the new depth are thrown away. Searching the previous best move first and keeping its result would make every budget worth a little more.
  • A transposition table. Manalath has a lot of transpositions: the same stones placed in a different order give the same position. Caching scores by a Zobrist hash, and using the stored best move to order the search, is the standard next step for any alpha-beta engine.
  • Tune the evaluation. The weights in the evaluation table were set by hand. With self-play games now cheap, they could be fitted instead.
